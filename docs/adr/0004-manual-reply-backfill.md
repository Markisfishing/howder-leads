# 0004 回覆改由業務人工回填，不讀業務信箱；每封開發信開一個案件

- 日期：2026-11-17
- 狀態：採用（2026-11-17 會議決議，使用者確認）
- 取代：SPEC v0.1 的 F-TRK-1（Graph 訂閱收件匣自動偵測回覆）與 `Mail.Read` 權限

## 背景
原本規劃用 Microsoft Graph 讀業務收件匣，依 `conversation_id` 自動判斷客戶有沒有回覆。2026-11-17 會議（團隊討論＋業界講評者問答）指出：
- 業務信箱裡有大量敏感資訊，判斷哪些信該回寫是資料治理問題，第一版不該碰。
- 客戶常用 LINE、微信、電話回覆，讀信箱也抓不到。
- 系統的價值在「把名單變成現金」：要能追蹤、催業務回報，並證明回覆率和成交數。

## 決定
- 寄出的每封開發信自動開一個**案件**（`sales_case`，由 `opportunity` 改名擴充）；不寄信也能「加入追蹤」開案。
- 客戶回覆由業務在案件上**人工回填**：管道、聯絡人、結果、備註、下次追蹤日、成交金額。回填會帶動公司狀態。
- 系統每天檢查逾期（寄出 7 天沒回填、過了下次追蹤日、14 天無回應），放進業務的待辦清單。
- Graph 只申請 **`Mail.Send`**，不申請 `Mail.Read`；不需要 Graph webhook。
- 之後要自動化時，採用「回信轉寄到專用信箱、系統比對案件、業務確認後才生效」的做法（SPEC F-TRK-1，M5 延伸）。

## 理由
- 權限只剩 `Mail.Send`，Microsoft 365 管理員比較容易核准（SPEC 11-4），也不會碰到業務的私人往來。
- 不需要外部連得進來的 webhook，部署可以放在公司內網（SPEC 11-3）。
- 所有管道（Email、LINE、微信、電話）都用同一種方式記錄，回覆率才算得準。
- 示範閉環只需要「100 筆名單＋一筆模擬回覆」，不必等信箱權限。

## 代價
- 要靠業務回填，所以催辦機制必須做好，否則資料會缺。
- 回覆時間是業務回填的時間，不是客戶真正回信的時間（回填表單允許填回覆日期）。
